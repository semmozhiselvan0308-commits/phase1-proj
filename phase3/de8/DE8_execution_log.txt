DE8 was performed to verify pipeline reliability.

4. TEST 2 — INVALID / REJECTED INPUT
====================================

Test file:

```
sms-call-internet-mi-2026-08-31.csv
```

The file was rejected during DE2 ingestion because it was missing the
required column:

```
internet_activity
```

Therefore, the file was correctly placed in the rejected directory
instead of the raw directory.

When DE7 validation was executed for logical date:

```
2026-08-31
```

the validation task expected the daily file in the raw directory.

The file was not present there because it had already been rejected.

Validation output:

```
ERROR: Expected daily file not found:
sms-call-internet-mi-2026-08-31.csv
```

Result:

PASS — EXPECTED FAILURE

Conclusion:

This was not a pipeline bug.

The pipeline correctly prevented invalid data from proceeding to
Spark processing and warehouse loading.

This demonstrates safe handling of rejected input.

5. TEST 3 — WAREHOUSE LOAD ENVIRONMENT FAILURE
==============================================

During the first DE8 warehouse test, the load_warehouse task failed.

The original error was related to the Windows Spark/Hadoop environment.

Important error:

```
java.lang.UnsatisfiedLinkError:
org.apache.hadoop.io.nativeio.NativeIO$Windows.access0
```

The environment was missing the required Hadoop configuration when
Spark was launched from the Airflow/WSL environment.

Investigation confirmed:

```
Python:
C:\Program Files\Python311\python.exe

Hadoop:
C:\hadoop

Hadoop winutils:
C:\hadoop\bin\winutils.exe

Hadoop DLL:
C:\hadoop\bin\hadoop.dll
```

A direct Windows Spark test was then performed.

Spark successfully started and successfully read the analytics
Parquet data.

Conclusion:

The warehouse failure was an environment/launch configuration issue,
not a problem with the Parquet data or warehouse logic.

======================================================================
6. FIX APPLIED TO DE7
=====================

The DE7 warehouse launcher was configured to explicitly provide the
Windows Python and Hadoop environment.

Important configuration:

```
PYSPARK_PYTHON =
C:\Program Files\Python311\python.exe

PYSPARK_DRIVER_PYTHON =
C:\Program Files\Python311\python.exe

HADOOP_HOME =
C:\hadoop

PATH includes:
C:\hadoop\bin
```

The DE7 warehouse task runs the patched DE6 warehouse builder using
this environment.

8. TEST 5 — IDEMPOTENCY / SAFE RERUN TEST
=========================================

Purpose:

To determine whether running the warehouse load again would create
duplicate records.

Warehouse row counts BEFORE rerun:

```
dim_time               = 5
dim_grid               = 10000
fact_network_activity  = 5
```

The load_warehouse task was executed again against the same analytics
data.

The task completed successfully:

```
Warehouse load completed.
Task instance in success state.
```

Warehouse row counts AFTER rerun:

```
dim_time               = 5
dim_grid               = 10000
fact_network_activity  = 5
```

Comparison:

```
Table                    Before       After

dim_time                    5            5
dim_grid                10000        10000
fact_network_activity       5            5
```

No row counts increased.

Conclusion:

PASS — IDEMPOTENT RERUN

The warehouse load can be rerun without creating duplicate rows.

The most important observation is:

```
fact_network_activity
Before = 5
After  = 5
```

If duplicate records had been inserted, this count would have
increased.

12. WHAT I LEARNED FROM DE8
===========================

DE8 was not only a testing phase.

It helped verify that a data pipeline should:

```
VALID DATA
    |
    v
PROCESS SAFELY
    |
    v
LOAD DATA
    |
    v
ALLOW SAFE RERUN
    |
    v
DO NOT CREATE DUPLICATES
```

It also demonstrated an important debugging principle:

When a downstream Airflow task fails, first identify the FIRST
actual failed task.

In the original DE8 run:

```
load_warehouse = FIRST FAILURE
```

while:

```
quality_check = downstream failure
notify         = downstream failure
```

Therefore, the root cause was investigated in load_warehouse rather
than incorrectly debugging quality_check or notify.
